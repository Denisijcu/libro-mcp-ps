Escritura permitida  : True
Destructivo permitido: True
1. Lectura           -> [OK] datos leidos
2. Escritura         -> [OK] algo escrito
3. Destructiva       -> [CONFIRMACION REQUERIDA]
--- flujo completo del token ---
[CONFIRMACION REQUERIDA]
Accion  : borrar_usuario:pruebas

Token   : 0E13E1A6  (valido 180 segundos, un solo uso)
Muestra este impacto al usuario, espera su aprobacion explicita y vuelve a llamar a la misma herramienta anadiendo confirm_token.
4. Token de otro objetivo -> [ERROR] El confirm_token no es valido, ha expirado, ya se uso, o pertenece a otra accion u otro objetivo. Pide uno nuevo.
5. Token correcto         -> [OK] usuario pruebas eliminado (simulado)
6. Reutilizar el token    -> [ERROR] El confirm_token no es valido, ha expirado, ya se uso, o pertenece a otra accion u otro objetivo. Pide uno nuevo.

CONFIRMA:
  - Con las dos puertas abiertas, lectura y escritura pasan sin friccion.
  - La destructiva sigue sin ejecutarse a la primera: devuelve impacto y token.
  - Caso 4: el token emitido para 'pruebas' NO sirve para 'otro'. El permiso
    esta atado al objetivo, no solo a la accion.
  - Caso 5: el token correcto deja pasar.
  - Caso 6: el mismo token ya no vale. Un solo uso.

DETALLE QUE ESTA EJECUCION DEMUESTRA Y NO ESTABA VERIFICADO:
  Un token rechazado NO se consume. En el caso 4 se intenta usar sobre 'otro',
  se rechaza, y en el caso 5 el mismo token sigue siendo valido para su objetivo
  legitimo. Si un intento fallido invalidara el token, cualquier error del modelo
  obligaria a repetir la confirmacion con el usuario, y eso empuja a la gente a
  desactivar el mecanismo.

OBSERVACION PARA EL TEXTO:
  El impacto se imprime ANTES de que exista ninguna posibilidad de ejecutar.
  Eso es exactamente lo que sostiene el argumento de la seccion 9.6: el token
  no da control de acceso, da visibilidad. La frase "Se eliminara la cuenta
  local 'pruebas'. No se puede deshacer." aparece en la conversacion pase lo
  que pase despues.
